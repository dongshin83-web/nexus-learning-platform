12-Week Plan

11~12주차는 앞선 학습을 하나의 campaign으로 묶는 구간입니다. Abaqus Python 자동화는 목적이 아니라 반복 가능한 evidence 생산 수단입니다. 최종 목표는 해석 조건, 결과, 불확실성, 다음 실험을 같은 형식으로 남기는 것입니다.

Campaign Architecture

좋은 simulation campaign은 한 번의 해석 결과가 아니라 질문, 모델군, sensitivity, evidence pack, 판단 memo가 연결된 구조입니다. 여기서는 계산을 많이 돌리는 것보다 계산 이유와 비교 기준을 선명하게 만드는 데 집중합니다.

Problem Frame

의사결정 질문 정의

해석이 답해야 할 질문을 stress, displacement, stiffness, fatigue, thermal risk 같은 관찰 가능한 결과로 바꿉니다.

  • 판단 기준과 단위를 먼저 정합니다.
  • 비교 기준이 hand calculation, test, previous model 중 무엇인지 기록합니다.
  • 결과로 결정할 항목과 결정하지 않을 항목을 분리합니다.
Model Family

baseline과 variant 구조

baseline 모델 하나와 parameter variant를 분리해야 결과 차이가 무엇 때문인지 추적할 수 있습니다.

  • geometry, mesh, material, BC, contact 중 바뀌는 항목을 명시합니다.
  • 한 번에 하나의 주요 가정만 바꾸는 비교군을 우선합니다.
  • model ID와 job ID 규칙을 통일합니다.
DOE / Sweep

민감도와 parameter sweep

모든 조합을 돌리기보다 uncertainty를 줄이는 변수부터 선택합니다.

  • mesh density, material property, friction, preload, thermal gradient를 후보로 둡니다.
  • 각 parameter가 어떤 risk를 줄이는지 적습니다.
  • 결과 metric은 max value보다 trend와 margin을 우선합니다.
Automation Boundary

자동화할 것과 남길 것

반복 실행, 결과 추출, 그림 저장은 자동화하기 좋습니다. 모델 가정 판단은 사람이 남겨야 합니다.

  • parameter injection과 job submission은 script 후보입니다.
  • warning 해석과 caveat 판단은 memo에 명시합니다.
  • script가 실패했을 때 재현 가능한 log를 남깁니다.
Data Extraction

ODB에서 결과 table로

결과 이미지만 남기면 비교가 어렵습니다. 핵심 output은 CSV/table 형태로 추출해 모델 간 비교가 가능해야 합니다.

  • RF, U, energy, peak stress, averaged hot spot metric을 추출합니다.
  • output 위치와 averaging rule을 함께 저장합니다.
  • plot은 같은 scale과 같은 legend 기준으로 저장합니다.
V&V / Correlation

검증과 현실 비교

verification은 계산이 의도대로 되었는가, validation은 현실을 대표하는가의 질문입니다. 둘을 같은 표에서 섞지 않습니다.

  • verification: RF balance, mesh sensitivity, warning status.
  • validation: test data, field observation, previous validated model.
  • correlation이 없으면 decision scope를 제한합니다.
Abaqus Python and Reproducibility

Abaqus Python은 숙련도 과시가 아니라 반복 가능한 해석 evidence를 만드는 장치로 봅니다. script는 해석 가정을 숨기지 않고, 오히려 더 잘 보이게 해야 합니다.

Script Template

parameter와 job 생성

geometry parameter, material value, load magnitude, mesh seed를 외부 table에서 읽어 job을 생성합니다.

  • input parameter file과 output folder를 분리합니다.
  • job name에는 model ID, parameter ID, date를 포함합니다.
  • script header에 Abaqus version과 단위계를 적습니다.
ODB Extraction

결과를 table로 추출

ODB에서 필요한 결과를 자동으로 뽑아 비교 table을 만듭니다.

  • node/RP displacement와 reaction force.
  • element set별 stress max와 averaged hot spot.
  • Explicit energy history와 time step 정보.
Logging

실행 이력과 실패 기록

자동화가 반복될수록 실패 원인을 추적할 log가 중요해집니다.

  • job status, warning count, error message를 요약합니다.
  • .msg/.sta/.dat 경로를 result table에 연결합니다.
  • 실패 job도 삭제하지 말고 triage 대상으로 남깁니다.
Do Not Automate Blindly

자동화하지 않을 판단

모델 idealization, BC 현실성, contact meaning, validation caveat는 자동화로 덮으면 안 됩니다.

주의: 자동화는 빠른 반복을 만들지만, 잘못된 가정을 빠르게 복제할 수도 있습니다.
Evidence Pack and Decision Memo

최종 산출물은 해석 결과 모음이 아니라 의사결정 가능한 evidence pack입니다. 계산 조건과 결과 그림, table, caveat, 다음 해석 queue가 같은 문서에 있어야 합니다.

Campaign Brief

질문과 판단 기준

해석 목적, failure mode, 판단 metric, pass/fail 또는 margin rule을 정의합니다.

  • 질문: 무엇을 결정하기 위한 해석인가?
  • metric: U, RF, Mises, Max Principal, energy ratio 등.
  • decision rule: 현재 결과로 가능한 판단 범위.
Assumption Register

모델 가정 목록

geometry simplification, material source, BC, load, contact, mesh rule을 한 표로 남깁니다.

  • 각 가정의 근거와 risk level을 적습니다.
  • 민감도 해석을 수행한 가정과 하지 않은 가정을 분리합니다.
  • 향후 test 또는 data로 닫아야 할 항목을 표시합니다.
Result Table

모델 간 비교

결과 이미지는 판단의 시작점이고, 비교는 table로 해야 합니다.

  • model ID, mesh level, solver, key parameter.
  • U, RF balance, stress metric, energy metric, warning count.
  • accepted, review required, rejected status.
Uncertainty Log

남은 불확실성

모든 불확실성을 해결하려고 하지 말고 의사결정에 영향을 주는 것부터 줄입니다.

  • mesh uncertainty, material uncertainty, BC uncertainty, validation gap.
  • 결론을 바꿀 수 있는 항목과 그렇지 않은 항목을 분리합니다.
  • 다음 simulation 또는 test의 목적을 연결합니다.
Two-Week Work Plan
Day 1

capstone question 정의

하나의 실제 또는 대표 문제를 골라 failure mode, 판단 metric, comparison 기준을 정합니다.

Day 2

baseline model evidence 정리

기존 모델 또는 새 baseline의 geometry, material, BC, mesh, solver 선택 이유를 표로 남깁니다.

Day 3

variant plan 작성

mesh, material, contact, load, thermal condition 중 어떤 parameter를 바꿀지 우선순위를 정합니다.

Day 4

Abaqus Python script skeleton

job naming, parameter table, result folder, log output 구조를 만들고 수동 실행과 비교합니다.

Day 5

ODB extraction 최소 자동화

RF, U, key stress, warning count 또는 energy history를 table로 뽑는 script를 만듭니다.

Day 6

campaign 실행과 result table 생성

baseline과 3~5개 variant를 비교해 trend와 anomaly를 표시합니다.

Day 7

V&V evidence 정리

verification evidence와 validation/correlation evidence를 분리해 작성합니다.

Day 8

uncertainty log 작성

결론을 바꿀 수 있는 불확실성과 다음 해석 또는 test로 닫을 항목을 정리합니다.

Day 9

decision memo draft

결과 요약, 판단 가능 범위, 보류 조건, 다음 action을 1~2페이지로 정리합니다.

Day 10

capstone review pack 완성

campaign brief, assumption register, result table, key plots, decision memo를 하나의 pack으로 묶습니다.

Deliverables
Deliverable 1

Simulation Evidence Memo v1

앞으로 반복 사용할 해석 검토 memo의 기본 형식을 확정합니다.

  • question, model assumptions, evidence, conclusion, caveat.
  • RF balance, mesh sensitivity, warning status 포함.
  • decision-ready와 review-required 항목 분리.
Deliverable 2

Capstone Campaign Pack

대표 문제 하나에 대한 해석 campaign 산출물을 묶습니다.

  • campaign brief와 assumption register.
  • baseline/variant result table.
  • 핵심 contour, XY plot, evidence figure.
Deliverable 3

Automation Script Plan

Abaqus Python으로 자동화할 반복 작업과 남겨야 할 수동 판단을 분리합니다.

  • parameter input, job submission, ODB extraction.
  • folder convention과 job naming.
  • warning/error log capture.
Deliverable 4

Operating Checklist

새 해석을 시작할 때 반복해서 사용할 체크리스트를 만듭니다.

  • problem framing, model fidelity, numerical reliability.
  • result evidence, V&V, decision readiness.
  • next simulation queue와 owner/action field.
Evidence Checklist
Campaign

campaign 구조 확인

  • 해석 질문, metric, decision rule이 먼저 정의되어 있는가?
  • baseline과 variant의 차이가 추적 가능한가?
  • 한 번에 너무 많은 가정을 바꾸고 있지 않은가?
Automation

재현성 확인

  • parameter, job, output folder, script version이 연결되는가?
  • ODB extraction 결과가 수동 확인값과 일치하는가?
  • 자동화가 모델 가정을 숨기지 않는가?
Decision

memo 완성도 확인

  • 현재 결과로 가능한 결정과 보류해야 할 결정이 분리되어 있는가?
  • verification과 validation evidence가 따로 정리되어 있는가?
  • 다음 해석 queue가 불확실성을 줄이는 순서로 정렬되어 있는가?
